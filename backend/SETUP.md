# Private workspace setup

Hosting remains GitHub Pages. Supabase supplies email-code authentication, PostgreSQL shared reports, role checks, and row-level security. Only a public publishable/anon key is shipped to the browser. No service-role key is needed in this app or in chat.

1. Create a Free Supabase organization/project and privately save the database password. The GitHub integration is not needed.
2. Copy the Project URL from Settings → Data API and the **Publishable** key from Settings → API Keys into `app/config.js`. These are public connection settings. Never use `sb_secret_` or a legacy `service_role` key.
3. Open the Supabase SQL Editor, create a new query, paste all of `backend/schema.sql`, and run it. The script is rerunnable and preserves existing records. It replaces this application's policies/triggers but does not delete reports. Initial owner: `israelmamann@gmail.com`. Verified `@thebigplan.com` addresses default to Viewer. Other addresses must have a current admin-created invitation.
4. Keep email confirmation enabled and anonymous sign-in disabled in Authentication settings. The website uses email codes. Email confirmation must remain enabled; the database rejects unverified access. Supabase internally creates a temporary password during new-user OTP signup, which is allowed without granting unverified report access. Configure Site URL as `https://israelmamann.github.io/dashboard/` and add this exact URL to Redirect URLs. The app explicitly requests this return URL for every sign-in email; localhost is never used as the default. After changing URL settings, request a fresh email instead of reusing an older link.
5. Under Authentication → Emails/Templates, configure **Magic Link** and **Confirm signup** to include the code, e.g. `<h2>Your Big Plan verification code</h2><p>{{ .Token }}</p>`. Custom templates require custom SMTP on current Supabase plans. This step is optional: the website also accepts Supabase’s default secure sign-in links. Link tokens are immediately removed from the URL and verified with Supabase before private data is loaded. Keep provider rate limits and expiry enabled.
6. Configure production email delivery under Authentication → Email/SMTP. Supabase's default mailer is generally limited to project team addresses and is unsuitable for company-wide signups. Use an existing SMTP provider or a verified-domain email service. A Gmail account with two-step verification can use smtp.gmail.com, port 465, its full email as username/sender, and a Google App Password entered directly into Supabase; that option does not require DNS changes. Never use a normal Gmail password in SMTP settings. Enter SMTP secrets directly in Supabase, not in chat or frontend files. Validate delivery to both the owner and a company-domain address before declaring team sign-in ready.
7. Build and test: `python deployment/prepare_preview.py`; `python deployment/prepare_workspace.py`; `python app/test_workspace.py`; `npm test --prefix backend`; `python prototype/test_new_groups.py`. The browser test uses a mock service; the PostgreSQL tests exercise real database functions/RLS in a local PostgreSQL WASM engine. Live Supabase/email tests are separate prerequisites.
8. Prepare a Pages commit with `python deployment/prepare_github_pages.py --workspace`. This publishes only authenticated frontend assets, public connection settings, and a fictional demo at `/demo/`; it never includes real sample records, SQL setup files, or local report archives. Push the exact commit to `gh-pages` without force, then verify the deployment URL.
9. Sign in as the owner with an actual emailed code or secure verification link. Upload the finalized baseline and current report in Administration. Sign out and sign in from another session to verify shared persistence. Check Viewer and Account manager restrictions against the live backend before team rollout.

## Stored information and permissions

Only the 16 normalized fields needed by the dashboard are stored. The database repeats the allowlist and discards unknown fields even if a client bypasses the browser parser. No raw CSV, SSN, dependent details, street address, date of birth, income, or unused source fields are stored. State and numeric age remain. Shared snapshots store daily complete reports; replacing a same-date report is atomic. Replacing the baseline recalculates comparisons.

All verified members may read report details, including the previously requested employee contact fields. Viewer export buttons are disabled and the server export RPC denies viewers. Account managers may export contacts but cannot upload, assign accounts, invite people, or change roles. Admins manage those operations. Because viewers can see contact fields, this is an export-action permission, not a claim that a viewer cannot manually copy information they can read.

Admin invitations grant approved access to an email address for seven days. The recipient uses the shared website link and requests their own code; the app does not send a separate invitation notification. Inviting an existing member updates their role. The owner cannot be demoted. Role changes, reports, and assignments update a small revision marker; clients check it once per minute and download full report payloads only when something changed.

Session tokens are stored in sessionStorage, not in the GitHub repository, URL, or application logs. Sign-out clears tokens and employee data from the UI and memory. The static site's HTML is public, but its private data is fetched only after verified membership; database policies enforce the boundary independently of frontend controls.

## Historical new-group limitation

A 2027 group absent from the 2026 report can be classified as new this year. That does not reveal which groups were new during 2026. Prior-year new-group totals/growth are unavailable without a 2025 report or reliable historical activation data. New-only filters must not manufacture a zero baseline. Whole-company comparisons and renewal comparisons continue to use their documented baselines.

## Checking stored report fields

Administration includes a Stored report field audit computed from the raw latest baseline/current arrays returned by load_dashboard, before browser-side field filtering. It reports row counts, unexpected field names and an observation timestamp without showing values. It does not audit older historical snapshots or claim de-identification. Names, email, phone, enrollment/carrier details, costs and numeric age remain sensitive data. Extra-field detection is distinct from removing all PHI. Browser tests explicitly verify that an unexpected ssn key is flagged, rather than hidden by the client allowlist; database tests verify such fields are discarded on save.
